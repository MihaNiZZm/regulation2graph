# Regulation2Graph

## О проекте

**Тип работы:** Магистерская исследовательская работа (НГУ)
**Стадия:** Начальная - тестирование гипотез и выбор инструментов
**Горизонт:** ~1.5 года до защиты

### Цель

Создание системы автоматического моделирования бизнес-процессов из текстов регламентов на естественном языке (русский язык).

### Постановка задачи

Бизнес-процессы (regulations) - например, процесс увольнения сотрудника - часто меняются из-за изменений во внешнем мире. Ручное моделирование связей таких процессов трудоёмко. Система должна автоматизировать извлечение структуры бизнес-процесса из текста регламента.

### Вход/Выход системы

- **Вход:** Текст регламента на естественном языке (русский)
- **Выход:** Модель бизнес-процесса в виде графа с:
  - Узлами-триплетами: `Субъект → Действие → Объект`
  - Связями очередности между действиями
  - Логическими ветвлениями (условия)

## Что реализовано

### 1. RuleBasedExtractor (`regulation2graph/core/extractor.py`)
- Извлечение триплетов `Triplet(actor, action, obj)` из предложений
- Поиск root-глагола (действие) через синтаксический разбор
- Поиск nsubj/nsubj:pass (актор) и obj/obl/iobj (объект)
- Лемматизация через Natasha MorphVocab
- Извлечение текста условия через `advcl` (adverbial clause)
- Детекция маркеров альтернативы: `иначе`, `в противном случае`
- **Присвоение `GatewayType.EXCLUSIVE`** триплетам с условием

### 2. Triplet Model (`regulation2graph/models/triplet.py`)
- Иммутабельный dataclass (`frozen=True`)
- Валидация в `__post_init__`
- Методы `to_dict()` / `from_dict()` для совместимости
- Properties: `has_condition`, `display_name`
- **`GatewayType` enum:** EXCLUSIVE, PARALLEL, INCLUSIVE
- **Поля:** `gateway_type`, `gateway_condition`

### 3. Settings (`regulation2graph/config/settings.py`)
- Централизованная конфигурация (маркеры условий, Neo4j, визуализация)
- Singleton через `@lru_cache`
- Поддержка переменных окружения

### 4. GraphVisualizer (`regulation2graph/graph/visualizer.py`)
- Построение NetworkX MultiDiGraph из триплетов
- **Gateway-узлы (Decision-узлы):** отдельный узел `◇ {condition}` для каждого условия
- **Логическое ветвление:** `(Event)-[:LEADS_TO]->(Gateway)-[:IF_TRUE]->(Next)` и `(Gateway)-[:IF_FALSE]->(Alternative | End)`
- Узел "Конец процесса" для условий без альтернативы
- Слияние альтернативных веток с основным потоком
- Цветовая маркировка: обычный/условный (gateway)/альтернативный/терминальный
- Сохранение в PNG

### 5. Neo4j Integration (`regulation2graph/graph/neo4j.py`)
- **`Neo4jLoader`** — загрузка графа в Neo4j через Docker
- **Схема данных:**
  - `(:Actor)-[:PERFORMS]->(:Event)`

  - `(:Gateway)-[:IF_FALSE]->(:Event | End)` — ветка "условие не выполнено"
- **Gateway-узел** хранит: `type`, `condition`, `uid`
- Автоматическая очистка БД перед загрузкой
- Docker Compose для быстрого запуска (`docker-compose.yml`)

### 6. Services Layer (`regulation2graph/services/`)
- **extraction_service.py:** `extract_process()`, `print_results()`

## Что НЕ работает (известные ограничения)

- ❌ **Кореференция** ("Менеджер проверяет заявку. Он отправляет её..." → "он" = ?)
- ❌ Пассивный залог ("Заявка подписывается директором")
- ❌ Безличные конструкции ("Необходимо согласовать бюджет")
- ❌ Объединение одинаковых сущностей (один актор = один узел)
- ❌ Синонимы (менеджер = руководитель)
- ❌ Вложенные условия ("если X, и если Y, то Z")
- ❌ Загрузка регламентов из файлов (только хардкод в main.py)
- ❌ **Параллельное выполнение** составных субъектов ("Менеджер и директор проверяют" → пока один составной актор, не AND-split)

## Архитектурные решения

### Логическое ветвление (Фаза 1)

**Принятые решения:**

1. **Gateway-узлы (Decision-узлы):** Для каждого условия создаётся отдельный узел типа `Gateway`.
   ```
   [Event]--[:LEADS_TO]-->[Gateway {condition: "..."}]
                              |--[:IF_TRUE]--> [Event (condition met)]
                              |--[:IF_FALSE]--> [Event (condition not met) | End]
   ```

2. **Слияние веток:** После условной и альтернативной ветки обе сливаются к следующему общему шагу.
   ```
   [Условие] --Да--> [Действие A] ---> [Общий шаг]
             --Нет--> [Действие B] -/
   ```

3. **Привязка "иначе":** Маркер альтернативы ("иначе", "в противном случае") относится к **последнему** условию в тексте.

4. **Терминальный узел:** Один узел "Конец процесса" на весь граф. Используется когда условие не имеет явной альтернативы.

5. **Типы Gateway:** `EXCLUSIVE` (XOR — либо одно, либо другое), `PARALLEL` (AND), `INCLUSIVE` (OR). Сейчас поддерживается только EXCLUSIVE.

**Пример:**
```
Вход: "Если документ согласован, менеджер подписывает. Иначе секретарь возвращает. Директор утверждает."

Граф:
[подписывает] --Да--> [утверждает]
              --Нет--> [возвращает] --> [утверждает]
```

**Neo4j модель:**
```cypher
(Event)-[:LEADS_TO]->(Gateway {type: "exclusive", condition: "документ согласован"})
(Gateway)-[:IF_TRUE]->(NextEvent)
(Gateway)-[:IF_FALSE]->(AlternativeEvent)
```

**Потенциальные улучшения (TODO):**
- [ ] Режим привязки "иначе" к первому условию (альтернативная стратегия)
- [ ] Вложенные условия ("если X, и если Y, то Z")
- [ ] Несколько терминальных узлов для разных сценариев завершения
- [ ] Поддержка PARALLEL и INCLUSIVE шлюзов
- [ ] **Параллелизм для составных субъектов:** "Менеджер и директор проверяют" → AND-split на два параллельных Transition с последующим AND-join

### Многоосновные предложения (Фаза 1.5) ✅ ЗАВЕРШЕНО

**Проблема:** Из предложения "Менеджер проверяет заявку и директор подписывает договор" извлекался только один триплет.

**Решение:** Модифицирован `_extract_actions_from_sentence()` для поддержки:
- Нескольких root глаголов (особенность парсера Natasha)
- Сочинённых глаголов через `conj` relation
- Наследования субъекта/объекта от root к сочинённым глаголам

**Поддерживаемые конструкции:**

| Конструкция | Пример | Результат |
|-------------|--------|-----------|
| Два независимых субъекта | "Менеджер проверяет и директор подписывает" | 2 триплета |
| Общий субъект, два глагола | "Менеджер проверяет и подписывает заявку" | 2 триплета (субъект наследуется) |
| Составной субъект | "Менеджер и директор проверяют заявку" | 1 триплет с составным актором |
| Три и более клаузы | "А делает X, Б делает Y, В делает Z" | 3 триплета |

**Ограничение:** Составной субъект ("Менеджер и директор") пока обрабатывается как один актор, а не как AND-split (параллельное выполнение). Это будет реализовано в Фазе поддержки PARALLEL шлюзов.

**Тесты:** 6 новых тестов в `tests/test_extractor.py::TestCompoundSentences`

**Поведение:**

### Фаза 2: Кореференция (СЛЕДУЮЩИЙ ШАГ)

**Цель:** Разрешение местоимений и анафорических ссылок.

**Проблема:**
```
"Менеджер проверяет заявку. Он отправляет её на согласование."
→ "он" = менеджер, "её" = заявка
```

Без кореференции система не свяжет "он" с "менеджер", и триплет будет неполным.

**Варианты решения (требуется анализ):**

| Подход | Библиотека | Плюсы | Минусы |
|--------|------------|-------|--------|
| Правила | Свой код | Простота, контроль | Ограниченная точность |
| DeepPavlov | `deeppavlov` | Готовая модель для русского | Тяжёлая зависимость |
| Natasha | `natasha` | Уже используется, NER есть | Нет полноценной кореференции |
| spaCy + coref | `spacy`, `coreferee` | Качественно для английского | Слабая поддержка русского |
| RuBERT-based | `transformers` | Высокое качество | Требует fine-tuning, GPU |
| LLM-based | API Claude/GPT | Отличное качество | Дорого, latency |

**Задачи:**
1. Исследовать существующие решения для русского языка
2. Протестировать DeepPavlov coref на примерах регламентов
3. Оценить правиловый подход (согласование по роду/числу/падежу)
4. Выбрать подход и реализовать интеграцию
5. Добавить тесты на кореференцию

**Ресурсы для изучения:**
- DeepPavlov Coreference: http://docs.deeppavlov.ai/en/master/features/models/coreference.html
- RuCoCo (Russian Coreference Corpus): https://github.com/dialogue-evaluation/RuCoCo

**Примечание:** Эмбеддинги для маркеров избыточны — достаточно словарей. Эмбеддинги могут понадобиться позже для Entity Resolution (объединение "менеджер" ≈ "руководитель"), но это отдельная задача.

### Фаза 7: Поддержка циклов (Loop) 📋 ПЛАНИРУЕТСЯ

**Цель:** Обрабатывать конструкции повторения в регламентах.

**Примеры:**
- "Пока документ не согласован, сотрудник вносит правки"
- "До тех пор, пока не получено одобрение, процесс повторяется"
- "При отклонении заявка возвращается на доработку" (неявный цикл)

**Открытые вопросы:**
- Как определить узел, к которому возвращаться? (нужен механизм резолва)
- Как визуализировать циклы в графе?
- Как отличить цикл от обычного условия?

**Задачи:**
1. [ ] Исследовать паттерны циклов в реальных регламентах
2. [ ] Определить маркеры циклов
3. [ ] Разработать механизм резолва целевого узла
4. [ ] Реализовать поддержку в WorkflowNet

### Фаза 8: Понимание контекста (Deep Learning) 📋 ПЛАНИРУЕТСЯ

**Цель:** Улучшить качество извлечения для сложных текстов.

**Подходы (исследование):**
1. **BERT для sequence labeling** - разметка BIO тегами (Actor, Action, Object, Condition)
2. **Fine-tuning на размеченном корпусе** - нужен датасет
3. **Гибридный подход** - BERT для разметки + правила для построения графа
4. **LLM (опционально)** - GPT/Claude для сложных случаев (дорого, но точно)

### Фаза 9: Сбор и разметка датасета 📋 ПЛАНИРУЕТСЯ

**Цель:** Создать качественный датасет для тестирования и обучения.

**Источники текстов:**

| Источник | Описание | Приоритет |
|----------|----------|-----------|
| **Синтетическая генерация** | LLM-генерация с контролем сложности | 🔥 Высокий (быстрый старт) |
| **Госуслуги** | gosuslugi.ru, pravo.gov.ru, regulation.gov.ru | Средний |
| **HR-порталы** | kadrovik.ru, hr-portal.ru — регламенты приёма/увольнения | Средний |
| **Академические корпуса** | OpenCorpora, Taiga, RuREBus | Низкий (не специфичны) |

**Структура датасета:**
```
data/
├── raw/                      # Исходные тексты
│   ├── synthetic/            # Сгенерированные
│   ├── government/           # Госрегламенты
│   └── corporate/            # Корпоративные
├── annotated/                # Размеченные данные
│   └── regulations.jsonl     # Формат: {text, triplets[], domain, complexity}
└── splits/                   # Train/val/test
```

**Формат разметки (JSONL):**
```json
{
  "id": "reg_001",
  "text": "Если документ согласован, менеджер подписывает договор.",
  "domain": "document_flow",
  "complexity": "medium",
  "triplets": [
    {
      "actor": "менеджер",
      "action": "подписывать",
      "object": "договор",
      "condition": "документ согласован",
      "spans": {"actor": [31, 39], "action": [40, 51], "object": [52, 59]}
    }
  ],
  "coreferences": []
}
```

**Задачи:**
1. Определить формат разметки (JSON schema)
2. Сгенерировать 20-30 синтетических примеров разной сложности
3. Найти и адаптировать 5-10 реальных коротких регламентов
4. Разметить вручную (триплеты, условия, кореференции)
5. Разделить на train/val/test

## Заметки для разработки

- Natasha использует модель NewsEmbedding - она обучена на новостях, может плохо работать на формальных текстах
- Условия извлекаются через синтаксическую связь `advcl` (adverbial clause)
- Triplet - иммутабельный, создавай новый вместо изменения
- Настройки (`get_settings()`) кэшируются, изменения требуют перезапуска
- Визуализатор использует бэкенд Agg (без GUI) - только сохранение в файл
- Граф сохраняется в `output/process_graph.png` по умолчанию
- **Gateway-узлы** в визуализации: оранжевые узлы с `◇ {condition}`
- **Neo4j** запускается через `docker-compose up -d`
- `main.py` — тонкий orchestrator, вся логика в `services/`
