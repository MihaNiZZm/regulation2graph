# Regulation2Graph

## О проекте

**Тип работы:** Магистерская исследовательская работа (НГУ)
**Стадия:** Начальная - тестирование гипотез и выбор инструментов
**Горизонт:** ~1.5 года до защиты

### Цель

Создание системы автоматического моделирования бизнес-процессов из текстов регламентов на естественном языке (русский язык).

### Постановка задачи

Бизнес-процессы (regulations) - например, процесс увольнения сотрудника - часто меняются из-за изменений во внешнем мире. Ручное моделирование связей таких процессов трудоёмко. Система должна автоматизировать извлечение структуры бизнес-процесса из текста регламента.

### Вход/Выход системы

- **Вход:** Текст регламента на естественном языке (русский)
- **Выход:** Модель бизнес-процесса в виде графа с:
  - Узлами-триплетами: `Субъект → Действие → Объект`
  - Связями очередности между действиями
  - Логическими ветвлениями (условия)

## Что реализовано

### 1. RuleBasedExtractor (`regulation2graph/core/extractor.py`)
- Извлечение триплетов `Triplet(actor, action, obj)` из предложений
- Поиск root-глагола (действие) через синтаксический разбор
- Поиск nsubj/nsubj:pass (актор) и obj/obl/iobj (объект)
- Лемматизация через Natasha MorphVocab
- Извлечение текста условия через `advcl` (adverbial clause)
- Детекция маркеров альтернативы: `иначе`, `в противном случае`

### 2. Triplet Model (`regulation2graph/models/triplet.py`)
- Иммутабельный dataclass (`frozen=True`)
- Валидация в `__post_init__`
- Методы `to_dict()` / `from_dict()` для совместимости
- Properties: `has_condition`, `display_name`

### 3. Settings (`regulation2graph/config/settings.py`)
- Централизованная конфигурация (маркеры условий, Neo4j, визуализация)
- Singleton через `@lru_cache`
- Поддержка переменных окружения

### 4. GraphVisualizer (`regulation2graph/graph/visualizer.py`)
- Построение NetworkX MultiDiGraph из триплетов
- **Логическое ветвление:** узел с условием → 2 исходящих ребра ("Да"/"Нет")
- Узел "Конец процесса" для условий без альтернативы
- Слияние альтернативных веток с основным потоком
- Цветовая маркировка узлов (обычный/условный/альтернативный/терминальный)
- Сохранение в PNG

### 5. Тесты (`tests/`)
- Unit-тесты для Triplet и RuleBasedExtractor
- Тесты для GraphVisualizer с логикой ветвления
- Бенчмарк по 3 категориям: Simple, Medium, Hard
- 24 теста, все проходят

## Что НЕ работает (известные ограничения)

- ❌ **Кореференция** ("Менеджер проверяет заявку. Он отправляет её..." → "он" = ?)
- ❌ Пассивный залог ("Заявка подписывается директором")
- ❌ Безличные конструкции ("Необходимо согласовать бюджет")
- ❌ Объединение одинаковых сущностей (один актор = один узел)
- ❌ Синонимы (менеджер = руководитель)
- ❌ Интеграция с Neo4j

---

## Архитектурные решения

### Логическое ветвление (Фаза 1)

**Принятые решения:**

1. **Слияние веток:** После условной и альтернативной ветки обе сливаются к следующему общему шагу.
   ```
   [Условие] --Да--> [Действие A] ---> [Общий шаг]
             --Нет--> [Действие B] -/
   ```

2. **Привязка "иначе":** Маркер альтернативы ("иначе", "в противном случае") относится к **последнему** условию в тексте.

3. **Терминальный узел:** Один узел "Конец процесса" на весь граф. Используется когда условие не имеет явной альтернативы.

**Пример:**
```
Вход: "Если документ согласован, менеджер подписывает. Иначе секретарь возвращает. Директор утверждает."

Граф:
[подписывает] --Да--> [утверждает]
              --Нет--> [возвращает] --> [утверждает]
```

**Потенциальные улучшения (TODO):**
- [ ] Режим привязки "иначе" к первому условию (альтернативная стратегия)
- [ ] Вложенные условия ("если X, и если Y, то Z")
- [ ] Несколько терминальных узлов для разных сценариев завершения

## План развития

### Фаза 1: Логическое ветвление ✅ ЗАВЕРШЕНО

**Цель:** При обнаружении условия граф должен ветвиться.

**Поведение:**
- Если условие выполнено → переход к следующему действию
- Если условие НЕ выполнено и альтернатива НЕ указана → переход в узел "Конец процесса"
- Если указано "иначе/в противном случае" → отдельная ветка

**Задачи:**
1. ✅ Расширить детекцию условий (извлекать текст условия через advcl)
2. ✅ Добавить детекцию маркеров альтернативы
3. ✅ Изменить структуру графа: узел с условием → 2 исходящих ребра
4. ✅ Добавить узел "Конец процесса" для неуказанных альтернатив
5. ✅ Обновить визуализатор для отображения ветвлений (MultiDiGraph)
6. ✅ Добавить тесты на ветвление (tests/test_visualizer.py)

### Фаза 2: Кореференция (СЛЕДУЮЩИЙ ШАГ)

**Цель:** Разрешение местоимений и анафорических ссылок.

**Проблема:**
```
"Менеджер проверяет заявку. Он отправляет её на согласование."
→ "он" = менеджер, "её" = заявка
```

Без кореференции система не свяжет "он" с "менеджер", и триплет будет неполным.

**Варианты решения (требуется анализ):**

| Подход | Библиотека | Плюсы | Минусы |
|--------|------------|-------|--------|
| Правила | Свой код | Простота, контроль | Ограниченная точность |
| DeepPavlov | `deeppavlov` | Готовая модель для русского | Тяжёлая зависимость |
| Natasha | `natasha` | Уже используется, NER есть | Нет полноценной кореференции |
| spaCy + coref | `spacy`, `coreferee` | Качественно для английского | Слабая поддержка русского |
| RuBERT-based | `transformers` | Высокое качество | Требует fine-tuning, GPU |
| LLM-based | API Claude/GPT | Отличное качество | Дорого, latency |

**Задачи:**
1. Исследовать существующие решения для русского языка
2. Протестировать DeepPavlov coref на примерах регламентов
3. Оценить правиловый подход (согласование по роду/числу/падежу)
4. Выбрать подход и реализовать интеграцию
5. Добавить тесты на кореференцию

**Ресурсы для изучения:**
- DeepPavlov Coreference: http://docs.deeppavlov.ai/en/master/features/models/coreference.html
- RuCoCo (Russian Coreference Corpus): https://github.com/dialogue-evaluation/RuCoCo

### Фаза 3: Работа с пассивным залогом и безличными конструкциями

**Цель:** Корректно извлекать триплеты из сложных конструкций.

**Задачи:**
1. Детекция пассивного залога через морфологические признаки (Voice=Pass)
2. Правила для инверсии субъекта и объекта в пассиве
3. Обработка безличных конструкций (actor = "Система" или контекстный)
4. Расширить бенчмарк категорией Hard

### Фаза 4: Объединение сущностей (Entity Resolution)

**Цель:** Если один субъект упоминается дважды, считать его за одну сущность.

**Задачи:**
1. Нормализация имён (лемматизация + регистр)
2. Создание реестра сущностей при обработке текста
3. Связывание повторных упоминаний с существующими узлами
4. Визуализация: один актор участвует в нескольких действиях

### Фаза 5: Интеграция с Neo4j

**Цель:** Хранить граф в Neo4j для запросов и анализа.

**Задачи:**
1. Создать модуль `regulation2graph/graph/neo4j_storage.py`
2. Схема данных: `(:Actor)-[:PERFORMS]->(:Action)-[:ON]->(:Object)`
3. Связи очередности: `(:Action)-[:NEXT]->(:Action)`
4. Условные связи: `(:Action)-[:IF {condition: "..."}]->(:Action)`
5. CRUD-операции и очистка базы

### Фаза 6: Работа с синонимами (Эмбеддинги)

**Цель:** "Менеджер" и "руководитель" должны распознаваться как одна сущность.

**Задачи:**
1. Интеграция эмбеддингов (RuBERT / Navec / fastText)
2. Порог семантической близости для объединения
3. Кластеризация похожих сущностей
4. Валидация на реальных текстах

### Фаза 7: Понимание контекста (Deep Learning)

**Цель:** Улучшить качество извлечения для сложных текстов.

**Подходы (исследование):**
1. **BERT для sequence labeling** - разметка BIO тегами (Actor, Action, Object, Condition)
2. **Fine-tuning на размеченном корпусе** - нужен датасет
3. **Гибридный подход** - BERT для разметки + правила для построения графа
4. **LLM (опционально)** - GPT/Claude для сложных случаев (дорого, но точно)

### Фаза 8: Сбор и разметка датасета

**Цель:** Создать качественный датасет для тестирования и обучения.

**Источники текстов:**

| Источник | Описание | Приоритет |
|----------|----------|-----------|
| **Синтетическая генерация** | LLM-генерация с контролем сложности | 🔥 Высокий (быстрый старт) |
| **Госуслуги** | gosuslugi.ru, pravo.gov.ru, regulation.gov.ru | Средний |
| **HR-порталы** | kadrovik.ru, hr-portal.ru — регламенты приёма/увольнения | Средний |

## Заметки для разработки

- Natasha использует модель NewsEmbedding - она обучена на новостях, может плохо работать на формальных текстах
- Условия извлекаются через синтаксическую связь `advcl` (adverbial clause)
- Triplet - иммутабельный, создавай новый вместо изменения
- Настройки (`get_settings()`) кэшируются, изменения требуют перезапуска
- Визуализатор использует бэкенд Agg (без GUI) - только сохранение в файл
- Граф сохраняется в `output/process_graph.png` по умолчанию
